# Day-to-Day Operations

← [Back to Infra Guide](index.md)

Once the platform is running, here's what you'll commonly need to do to keep it healthy.

---

## Starting and stopping

To start (or restart) the full stack, include the profile for your chosen ingress mode:

```bash
# Direct (no extra profile)
docker compose up -d

# Cloudflare Tunnel
docker compose --profile cftunnel up -d

# VPN edge
docker compose --profile vpnedge up -d
```

To shut it all down gracefully (include the profile so Docker also stops the profile-gated container):

```bash
docker compose down
# or, if a profile was active:
docker compose --profile cftunnel down
docker compose --profile vpnedge down
```

This stops and removes the containers, but **does not delete any data** — everything in `.vols/` is preserved.

If you only want to restart a single service (for example, after changing its configuration in `.env`):

```bash
docker compose up -d --no-deps --force-recreate gitlab
```

Replace `gitlab` with the name of whichever service you want to restart. The `--force-recreate` flag is important — it ensures the container is rebuilt from scratch so it picks up any new environment variables.

> **Note**: `docker compose restart <service>` does not re-read environment variables from `.env`. Always use `up -d --force-recreate` if you've changed configuration.

## Viewing logs

To watch all services at once:

```bash
docker compose logs -f
```

To watch a specific service:

```bash
docker compose logs -f gitlab
docker compose logs -f keycloak
docker compose logs -f traefik
```

Press `Ctrl+C` to stop watching. The logs continue running in the background.

To see the last 100 lines of logs without following:

```bash
docker compose logs --tail=100 gitlab
```

---

## Checking service health

```bash
docker compose ps
```

This shows the current state of every container. A healthy service shows `healthy` in the Status column. If something shows `unhealthy` or keeps restarting, check its logs.

## Where data lives

All persistent data is stored under `.vols/` in the project root. This folder is git-ignored — it won't be committed to version control. It contains:

- `.vols/gitlab/` — GitLab repositories, registry images, uploads, and configuration
- `.vols/gitlab-runner/` — GitLab Runner configuration and build cache
- `.vols/vault/` — OpenBao secrets storage
- `.vols/keycloak-db/` — legacy cold copy of shared PostgreSQL (if present after migration); live data is Docker volume `dsoaas-postgres-data`
- `.vols/mongo/` — legacy cold copy of MongoDB (if present after migration); live data is Docker volume `dsoaas-mongo-data`
- `.vols/traefik/` — ACME certificate storage (your Let's Encrypt certificates)

Treat this entire folder as sensitive. Anyone with access to these files can potentially extract secrets or impersonate users.

## Backups

The platform stores all durable state under **`.vols/`** plus your **`.env`** at the repo root. Both are git-ignored.

### Creating an archive

From the repository root:

```bash
make backup
```

This runs [`bootstrap/backup.sh`](../../bootstrap/backup.sh), which writes `backups/platform-<timestamp>.tar.gz` containing `.env` (if present) and `.vols/`, while skipping bulky rebuildable paths (for example GitLab build caches and logs, and local `node_modules`). The `backups/` directory is listed in `.gitignore` — treat archives as **sensitive** (they include secrets and full GitLab data).

**Retention:** keep a small number of recent archives on separate storage (external disk or object storage). Rotate old files manually; there is no built-in retention job. Duplicate same-day `platform-*.tar.gz` files are safe to delete after you confirm the newest restore works.

## Deploy kubeconfig API URL (Docker Desktop)

In-stack GitLab Runner job containers share `devops-network` with `k3d-dsoaas-serverlb`. CI kubeconfigs should use:

`https://k3d-dsoaas-serverlb:6443`

not `https://host.docker.internal:16443` — on Docker Desktop (Windows) that hairpin often TLS-times-out and deploy jobs fail at `kubectl create secret` / OpenAPI validation.

- Regenerated by `bootstrap/runner-rbac.sh` (default `KUBE_API_CI_URL`)
- Deploy jobs also rewrite the server URL at runtime when the in-stack LB is reachable (`configs/auto-devops-pipeline`). Probe with **curl** (not alpine wget): k3s `/livez` often returns **401**, and wget treats that as unreachable, which skips the rewrite and then `kubectl` TLS-times-out on `host.docker.internal:16443`.

## Disk hygiene (Docker Desktop + GitLab registry)

CI job **artifacts** live in MinIO and stay small (short `expire_in` in pipelines). The hosts that grow are:

| Store | Path / location | Typical growth |
|---|---|---|
| Docker Desktop VHDX | `%LOCALAPPDATA%\Docker\wsl\disk\docker_data.vhdx` | Job images, k3d, unrelated local images/volumes |
| GitLab Container Registry | `.vols/gitlab/data/gitlab-rails/shared/registry` | Kaniko app images + `${image}/cache` layers |
| Mongo WiredTiger journal | named volume `dsoaas-mongo-data` (`/data/db/journal`) | WAL leak on NTFS bind mounts; live data must stay on a named volume |
| Platform backups | `backups/` | Full `.vols` archives |

Task Manager **System** (PID 4) often shows high disk during builds: WSL2 VHDX I/O and NTFS registry writes are attributed to the kernel, not `Docker Desktop`.

### Reclaim host Docker disk

Optional maintainer script (not part of greenfield bootstrap):

```bash
make prune-docker-host                 # containers, dangling images, build cache, networks
make prune-docker-host ARGS='--images' # also unused images (not referenced by any container)
make prune-docker-host ARGS='--retention-days'    # unused images older than GITLAB_RUNNER_IMAGE_RETENTION_DAYS (default 7)
make prune-docker-host ARGS='--retention-days 7'  # same with an explicit day count
```

`--images` removes large unused tags (old GitLab CE versions, stopped side projects) with **no age gate**. It does **not** touch images used by running/stopped containers or GitLab registry blobs under `.vols/`.

`--retention-days` runs `docker image prune -af --filter until=<N*24>h`: unused images whose **creation time** is older than N days. That pairs with runner `GITLAB_RUNNER_PULL_POLICY=if-not-present` (see [Env → Runner pull policy](02_env.md#runner-pull-policy-and-image-retention)): jobs skip pulls while the image exists locally; after retention removes it, the next job pulls fresh. Prefer a daily or weekly schedule (cron / Task Scheduler) outside heavy CI waves — prune is **not** run on runner start.

Trade-offs with `if-not-present`: floating tags (`:latest`, security scanners) stay stale until retention (or a manual `docker rmi`) removes them; corrupt local layers do not self-heal on every job (use prune / `docker rmi` then retry). Rollback: set `GITLAB_RUNNER_PULL_POLICY=always` and recreate `gitlab-runner`.

After a large prune on **Windows Docker Desktop**, free space does not return to `C:` until the VHDX is compacted (admin PowerShell):

```powershell
wsl --shutdown
Optimize-VHD -Path "$env:LOCALAPPDATA\Docker\wsl\disk\docker_data.vhdx" -Mode Full
```

If `Optimize-VHD` is unavailable, use Docker Desktop → **Settings → Resources → Resource Saver / Clean / Compact** (wording varies by version), or [Docker’s disk reclaim docs](https://docs.docker.com/desktop/settings-and-maintenance/reclaim-disk/).

### Disk watchdog (failsafe)

GitLab CE has no maintenance mode. A hard `compose stop` while a push is in Gitaly quarantine is how default branches went missing. The host watchdog **blocks new work, waits, then stops services in order**.

This section is the **Compose-host (Windows) backend** only. Linux Compose, Kubernetes, and the shared policy contract are [milestone 05 — failsafe backends](../XX_milestone/05_failsafe_backends.md).

Must run on the **host** (Git Bash / Task Scheduler). A container `df` sees the Docker VHDX, not `C:` where `.vols/gitlab` lives.

```bash
make watchdog                      # one check (safe to schedule every 1–2 min)
make watchdog ARGS='--loop 120'    # long-running
make watchdog ARGS='--dry-run'
make watchdog ARGS='--test-email'  # SMTP + WATCHDOG_NOTIFY_EMAILS
make watchdog ARGS='--clear'       # after a trip; then docker compose up -d
```

Two tiers (`.env`, GiB free on the repo filesystem):

| Var | Default | Action |
|---|---|---|
| `WATCHDOG_WARN_FREE_GB` | `80` | Email **warning** once per excursion |
| `WATCHDOG_SHUTDOWN_FREE_GB` | `50` | Quiesce → drain → ordered stop |

Emails (same `SMTP_*` as GitLab/Keycloak) to `WATCHDOG_NOTIFY_EMAILS`: warning, shutdown-init, shutdown-failing (drain timeout or a `compose stop` group failed), shutdown-successful.

Shutdown sequence (timeouts are env, defaults are slow on purpose):

1. **Quiesce** — SIGQUIT `gitlab-runner`; Traefik catch-all 503
2. **Drain** — wait up to `WATCHDOG_DRAIN_SECONDS` (default **3600**) for `runner-*` and `git-receive-pack`
3. **Stop** — runner → gitlab (`WATCHDOG_GITLAB_STOP_TIMEOUT`, default **900**) → apps → MinIO → mongo/postgres (`WATCHDOG_DATA_STOP_TIMEOUT`) → IdP → Traefik

State: `.vols/watchdog.state` (`ok` / `warned` / `draining` / `stopped`). The watchdog **never** brings the stack back up.

Every tick also runs `make gitaly-promote-incoming` so leftover `tmp_objdir-incoming-*` objects are merged even when disk is healthy (this is the “empty branches / stuck MR” bug).

Windows Task Scheduler (logged-on user, so Docker Desktop is available):

Use `bootstrap/watchdog-hidden.vbs` (wscript, window style 0) so Task Scheduler does not flash a CMD window every tick. `watchdog.cmd` remains the real entrypoint.

### Reduce Defender I/O amplification (local ops)

Windows Defender realtime scanning of the VHDX and `.vols` registry blobs can multiply disk traffic. Optional **local** exclusions (do not commit machine-specific paths into the stack):

- `%LOCALAPPDATA%\Docker\wsl\disk\`
- Repo `.vols\gitlab\data\gitlab-rails\shared\registry\`
- Repo `.vols\minio\data\` (optional)

Only add exclusions you accept from a security standpoint on a dedicated DevSecOps host.

### GitLab registry retention (prevents `.vols` growth)

This stack uses the **registry metadata database** (`REGISTRY_DB_ENABLED=true`). Offline `gitlab-ctl registry-garbage-collect` is **not compatible** and will refuse to run. Untagged layers are removed by **online GC** (continuous; typically ~24h after a tag/manifest becomes unreferenced).

**Apply / re-apply cleanup policies** on all registry-enabled projects (optional maintainer script):

```bash
./bootstrap/gitlab-registry-retention.sh           # enable policies
./bootstrap/gitlab-registry-retention.sh --trigger # also run the expiration worker now
```

Default policy (Auto DevOps–friendly):

| Setting | Value | Purpose |
|---|---|---|
| `enabled` | `true` | Run on cadence |
| `cadence` | `1d` | Daily evaluation |
| `keep_n` | `5` | Keep newest N tags **per project** (GitLab allows 1\|5\|10\|25\|50\|100 only; not a platform-wide cap) |
| `older_than` | `7d` | Only delete tags older than this |
| `name_regex` | `.*` | Candidates for deletion |
| `name_regex_keep` | `latest-.*` | Protect Kaniko branch tip tags (`latest-develop`, etc.) |

UI equivalent: **Settings → Packages and registries → Container registry → Clean up image tags**.

**Space reclaim timeline:** policy deletes eligible tags → manifests become unreferenced → online GC removes blobs (often within ~24–48h). Tags newer than `older_than` are kept even if there are many of them. There is no GitLab setting for “100 tags across the whole platform.” Monitor with:

```bash
docker exec gitlab gitlab-ctl registry-database gc-stats
```

Pipeline control: set CI variable `KANIKO_CACHE=false` on a project to disable Kaniko remote cache pushes when disk is tight (slower builds, less registry growth). Re-seed pipelines with `make update-dso-configs` after template changes.

### Mongo WiredTiger journal (prevents named-volume / `.vols` blow-up)

Logical Management API data is tiny. Disk growth is almost always `WiredTigerLog.*` (100MB each). On a **Windows NTFS bind mount**, WiredTiger does not archive logs after checkpoint — that is what produced the ~300G leak. Live data is the named volume **`dsoaas-mongo-data`** (ext4 in the Docker VHDX), same pattern as Postgres. A leftover `.vols/mongo` directory is only a pre-migration cold copy.

**Do not delete journal files while `mongod` is running.** They are a sequential WAL; removing a subset corrupts recovery.

Runtime bound (`mongo/mongod.conf`): `log=(archive=true)`, `checkpoint=(wait=60,log_size=256MB)`, cache 1GB.

**Reclaim** when file count **> 100** or any log is **older than 7 days** (should not happen on the named volume):

```bash
./bootstrap/mongo-journal-retention.sh            # report; exit 1 if over limit
./bootstrap/mongo-journal-retention.sh --apply    # clean-stop mongo, wipe journal, start
```

`--apply` stops `mongo` (Management API is down for that window), refuses to unlink logs if `mongod.lock` is still non-empty, then recreates the container. After a clean stop every journal file is obsolete — the script deletes all `WiredTigerLog.*`, not “last 100”, because a hole in the log sequence is unsafe.

`make backup` also writes `backups/mongo-<stamp>.archive.gz` (`mongodump`) because the named volume is not inside `.vols/`.

Monitor:

```bash
docker exec mongo sh -c 'ls /data/db/journal/WiredTigerLog.* | wc -l'
docker exec mongo du -sh /data/db/journal
```

### Restoring

1. Stop the stack so files are not locked: `docker compose down` (include `--profile …` if you use Cloudflare Tunnel or VPN edge).
2. Extract the archive:

```bash
make restore ARCHIVE=backups/platform-YYYYMMDD-HHMMSS.tar.gz
```

3. Start Compose again (`docker compose up -d` with the right profile), then re-run Kubernetes bootstrap steps if needed (`./bootstrap/bootstrap.sh` or the individual `bootstrap/*.sh` scripts after k3d).

`restore.sh` refuses to run while any Compose container for this project is still running.

### Reset without a backup

If you only need to wipe Kubernetes state but keep GitLab/Vault volumes, use `make reset`. For a full wipe including `.vols`, see [Reset from zero](05_reset_from_zero.md) and `make reset ARGS=--all` (interactive confirmation).

## Upgrading services

This platform pins specific image versions in `docker-compose.yml` to prevent unexpected behavior from automatic updates. To upgrade a service:

1. Update the image tag in `docker-compose.yml` (e.g., change `gitlab/gitlab-ce:18.10.1-ce.0` to a newer version)
2. Pull the new image: `docker compose pull <service-name>`
3. Recreate the container: `docker compose up -d --no-deps --force-recreate <service-name>`
4. Check logs for any migration errors: `docker compose logs -f <service-name>`

### Guided GitLab upgrade (`make upgrade`)

For GitLab, [`bootstrap/upgrade.sh`](../../bootstrap/upgrade.sh) automates the runbook above — backup, tag rewrite, pull, recreate, health wait, and an optional matching `gitlab-runner` bump:

```bash
# Pin an explicit target version:
make upgrade gitlab VERSION=18.11.2-ce.0

# Or omit VERSION to resolve the latest published tag (you still confirm before it runs):
make upgrade gitlab
```

It resolves the current pinned tag, prompts you to confirm the upgrade path, runs `make backup`, rewrites the tag in `docker-compose.yml` (keeping a `*.bak` for rollback), recreates only the `gitlab` container, and waits for it to report healthy. It then offers (with confirmation) to bump `gitlab-runner` + `helper_image` to the matching version.

When `VERSION` is omitted, the script queries Docker Hub for the highest published `gitlab/gitlab-ce` tag and shows it as the proposed target. **The latest may be several stops ahead of your current version** — the confirmation prompt is your chance to verify the upgrade path and, if needed, re-run with an explicit intermediate `VERSION=<tag>` instead.

Flags (set as make variables): `SKIP_BACKUP=1`, `ASSUME_YES=1` (non-interactive; also auto-accepts an auto-resolved latest version), `RUNNER_VERSION=X.Y.Z` (override derived runner version), `HEALTH_TIMEOUT=<seconds>` (default 900). Run the command once per required upgrade stop.

**GitLab upgrades require special care.** GitLab has a strict version upgrade path — you cannot skip from a very old version to a very new one without going through intermediate versions. Always check the [GitLab upgrade path tool](https://gitlab-com.gitlab.io/support/toolbox/upgrade-path/) before upgrading.

For other services, minor version bumps are generally safe. Major version bumps may have breaking changes — check the service's release notes before upgrading.
